# Global Rule: Swarm Quality Doctrine (Measured Anti-Patterns)

These directives encode measured, published findings about multi-agent systems (Anthropic's multi-agent research plus SwarmForge's own field forensics). They bind `domain-architect` (design time), `persona-engineer` (write time), and `prompt-evaluator`/`qa-validator` (evaluation time) for every generated swarm.

**Directives:**

1. **Single-Agent Justification (burden of proof on decomposition):** Multi-agent systems cost 3–15x the tokens of an equivalent single agent, and a well-designed single agent with appropriate tools can accomplish far more than most developers expect. Every blueprint MUST state in `single_agent_justification` why one well-tooled agent cannot do the job — the only valid grounds are context pollution, genuinely parallel independent workstreams, or a specialization threshold. Evaluators reject blueprints without it. This is the necessity floor that complements the existing right-sizing ceiling (5–9 roles).

2. **Context-Boundary Decomposition, Not Phase Decomposition:** Splitting one body of work into sequential pipeline stages ("planner → implementer → tester → reviewer") is a measured anti-pattern — each handoff loses context ("telephone game"). Group tasks that share necessary context into ONE agent: the agent implementing a feature also writes and runs its tests. GOOD boundaries: independent research paths, components with defined APIs, blackbox verification of finished output (a fresh-context reviewer IS a good boundary — it must not share the implementer's context). BAD boundaries: sequential phases of the same work, tightly coupled components, anything needing constant state sync. `prompt-evaluator` flags phase-chain rosters as a category error routed back to `domain-architect`.

3. **Density, Not Mass (prompt budget):** Generated prompts are judged by operational depth, not length. Every generated file must be complete — role-specific responsibilities, constraints, error handling, output format — with ZERO boilerplate padding; a long file whose length comes from filler measurably buries its own critical instructions. Hard bounds: every generated rule file stays under Antigravity's 12,000-character limit; the generated root `AGENTS.md` stays focused on orchestration (target well under ~15,000 characters), with non-orchestration content modularized into `.agents/rules/` (conditional rules via `trigger: model_decision`/`glob` load only when relevant, keeping sessions lean). `qa-validator` flags generated files that exceed these bounds or pad with repetition.

4. **Verifier Hardening ("early victory" countermeasure):** Verification agents are documented to produce false positives — declaring work done without thorough checking. Every generated verifier/reviewer/QA persona MUST carry explicit completeness language: "you MUST run the complete check suite before reporting", "you MUST test edge cases", "every PASS must cite the mechanical check (command/grep/diff) that produced it" — never a vague "verify this works". A generator agent NEVER approves its own output; verification always runs in a fresh-context agent. Fresh-context reviewers flag only correctness and requirement gaps, NOT style preferences — an evaluator told to find gaps will always find something, and nit-chasing causes over-engineering. (SwarmForge applies this discipline to itself; this directive makes `persona-engineer` propagate it into every generated swarm's verifiers.)

5. **Manifesto Verbatim, Artifacts Just-in-Time:** The user's original request and vision pass down VERBATIM (Visionary Context Passing — never compressed; the Generation Contract and Manifesto Fidelity Check already enforce this). Research artifacts, file contents, and large reference material are the opposite: pass lightweight identifiers (paths, queries, report filenames) and let each agent load what it needs at runtime via its tools — do not pre-dump bulk content into every delegation prompt. The Generation Contract's constraint payload is the deliberate exception: it travels verbatim because rules do not reliably reach subagent contexts.

6. **Tool Design Standards (for `tool-smith` and `mcp-integrator`):** Consolidate related operations into fewer, higher-level tools rather than many narrow API-mirroring ones — if a human engineer can't tell which of two tools to use, neither can an agent. Use consistent prefix namespacing for related tools. Custom tools return semantically meaningful identifiers (not opaque UUIDs), support concise/detailed response formats where output can be large, and emit actionable error messages that let the calling agent self-correct.
